# Opportunity Scan

**Purpose.** A more frequent, lighter-weight pass than `weekly-scan.md`: surface assets — from the current watchlist and from a fresh scan — that look like they have real upside potential right now. Unlike the other routines, this one is allowed to act on what it finds: it can add or remove watchlist symbols on its own conviction, and — after cross-checking `earnings-watch` and `weekly-scan` findings — it can surface an actual trade proposal via `propose-trade`. It never places an order itself; that always still requires the user's explicit confirmation.

**Schedule.** Weekdays, every 2 hours starting at market open: 9:30 AM, 11:30 AM, 1:30 PM, and 3:30 PM ET — all within regular market hours (9:30 AM–4:00 PM ET); the next 2-hour step (5:30 PM) would land after the 4:00 PM close, so the day stops at 3:30 PM. One Routine, since all four times share the same :30 minute:
- "Opportunity Scan (every 2h, 9:30am-3:30pm ET)" (`trig_01XUD48NBPSqJB98FuKbnPnu`), cron `30 13,15,17,19 * * 1-5` (UTC).

Self-bound to the session at `session_01WAYdETVewPXXJGZ9qTaTAa` (self-bind was required to retain Robinhood connector access — the org doesn't support attaching connectors to fresh-session triggers). The UTC hours are correct for 9:30 AM/11:30 AM/1:30 PM/3:30 PM ET while EDT is in effect; they'll need updating to `30 14,16,18,20 * * 1-5` when clocks fall back to EST in November.

**Market-day safety net.** The `1-5` cron field restricts firing to Monday–Friday, but cron has no concept of US market holidays (Thanksgiving, Christmas, etc.) — a firing on a holiday would still reach this routine. There's no holiday-calendar tool available to check in advance, so step 0 below is a live, in-routine check instead: if the market isn't actually open right now, the routine recognizes that from live quote data and stops early with a one-line journal note, rather than running the full scan against stale or non-existent session data.

**Steps.**
0. **Confirm the market is actually open before doing anything else.** Pull `get_equity_quotes` for one or two watchlist symbols and check the quote's `state` field and trade timestamp freshness. If `state` isn't `active`, or the last trade timestamp is stale relative to now, the market is closed today (most likely a holiday the `1-5` cron can't know about) — stop here, skip the rest of the steps, and journal a one-line note ("market closed today, skipping") rather than running the full scan against dead data.
1. Build the candidate set:
   - Every symbol currently on `memory/watchlist.md`.
   - A fresh scan for new candidates: `get_scans` for an existing bullish/momentum-oriented scan, `run_scan` on it (or `create_scan` if nothing suitable exists), same liquidity bar as `weekly-scan.md`.
   - **Junk filter:** drop any scan hit with an empty `market_cap` field — this is the mechanical signature of leveraged/inverse ETFs, ETNs, and basket/trust products (the scanner has no native filter for this, but every real operating company has a populated market cap and every leveraged/basket product observed so far doesn't). Note the count skipped.
   - **Catalyst context:** read the latest `weekly-scan` journal entry for catalyst-calendar findings (FDA dates, index rebalances, M&A chatter, conferences) and connect them to any candidate that lines up.
   - **Momentum-building watch:** same journal entry — check `weekly-scan`'s "building momentum" names (rising RSI over multiple sessions, no single day extreme enough to hit that scan's own threshold). If one of them shows up as a scan hit or watchlist mover this run, say so explicitly — it's a name already flagged as accumulating, not a surprise move.
2. For each surviving candidate, pull `get_equity_technical_indicators` and `get_equity_historicals` (and `get_equity_fundamentals` for anything not already vetted by `weekly-scan.md`) to assess whether there's a real, current upside signal — not just "still on the list." Include trend context (SMA 50/200 — is the move with or against the prevailing trend) and, for anything clearing the first screen, the nearest support/resistance level from the `pivot_points` indicator.
3. Filter hard. This runs three times a day — report only what actually changed or stands out since the last pass (new breakout, momentum turning up, approaching a level from the thesis, a new scan hit). A routine that reports the same unchanged symbols every run trains the user to ignore it.
4. **Watchlist management.** For a new candidate that clears the repo's usual conviction bar (real, current signal; no bad news, no major concerns — the same bar used for every watchlist addition in this repo), add it directly via the `watchlist-add` skill — no need to wait for confirmation, per `CLAUDE.md` guardrail 8. For an existing watchlist symbol whose thesis has clearly broken (bad news landed, the technical setup failed, the original catalyst is gone), remove it via `watchlist-remove`. Always journal the specific reasoning for any add/remove.
5. **Trade proposal (optional).** For anything — new or already on the watchlist — that looks compelling enough to actually trade, cross-check before proposing:
   - **Earnings timing:** read the most recent `earnings-watch` journal entry; if it's stale or never covered this symbol, run `get_earnings_calendar` for it directly. Don't propose walking into a print.
   - **Deeper vetting:** read the most recent `weekly-scan` journal entry for prior fundamentals/technicals work on this symbol; if none exists, pull `get_equity_fundamentals` directly (the same sanity-check `weekly-scan` would do) before proceeding.
   - Only after both come back clean, invoke `propose-trade` for that symbol. This step is optional — most runs won't produce one, and that's fine. Don't stretch a marginal setup into a proposal just to have one.
6. Report directly to the user in the conversation — symbol, the specific signal, current price/level, one line on why it's worth a look now, plus anything added/removed from the watchlist and whether a trade proposal is attached. If there's genuinely nothing new, say that plainly and keep it short; don't manufacture a report out of noise.

**Guardrails.** Never calls `place_equity_order`/`place_option_order` itself — `propose-trade` still requires the user's explicit confirmation before any order executes, per `CLAUDE.md` guardrail 1, no matter how this routine surfaced the idea. Watchlist adds/removes are self-authorized (guardrail 8) but must still be journaled with reasoning and mirrored to the Robinhood "Agentic Watchlist." A trade proposal must not be made without first checking `earnings-watch` and `weekly-scan` findings for that symbol. `propose-trade`'s own guardrails (20% sizing, 7-position cap, no fixed cash reserve, -8% stop, 2-proposals/week cap) still apply once invoked.

**Journal output.** Append to `memory/journal/<date>.md`: which scan/watchlist symbols were checked, what stood out and why (including trend/SMA and nearest pivot level, and any catalyst tie-in) — or that nothing new stood out, how many scan hits were skipped as junk (empty market_cap), any watchlist adds/removes with reasoning, and — if applicable — the trade proposal drafted (with the earnings-watch/weekly-scan cross-check noted) and the user's decision on it if resolved in the same turn. If step 0 found the market closed, a one-line entry noting that is enough — no need for the full template.

**Dashboard output.** After journaling, rebuild and republish the "Agentic Trading Desk" Artifact (see `.claude/skills/trading-dashboard/`) so it reflects this run.
