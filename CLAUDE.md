# CLAUDE.md

Standing instructions for any Claude Code session — interactive or a scheduled Routine — working in this repo. See `README.md` for the full strategy.

## Guardrails

1. **Propose + Confirm only.** Never place an order (equity or option) without the user explicitly confirming it in that conversation. Research, analyze, and propose — execution requires a human "yes."
2. **Agentic account only.** Trade exclusively through the Agentic Robinhood account (••••6245). Do not act on any other linked account.
3. **Respect the risk guardrails** in `README.md` on every proposal: max 20% of account value per position, max 7 concurrent open positions, -8% stop-loss, max 7 new proposals/week. No fixed minimum cash reserve — `propose-trade` sizes each position at its own judgment up to these caps, including up to full deployment when warranted.
4. **Journal every routine run.** After any routine (scheduled or manual) touches the portfolio, watchlist, or a scan, append an entry to `memory/journal/<YYYY-MM-DD>.md` (create the file if today's doesn't exist yet) using the format in `memory/README.md`.
5. **Keep the watchlist current — in both places.** When the user approves adding, removing, or updating the thesis on a symbol, reflect it in `memory/watchlist.md` **and** mirror the add/remove to the Robinhood "Agentic Watchlist" (list_id `aaf2fa51-2240-4463-8af2-d8c8b0621302`, via `add_to_watchlist`/`remove_from_watchlist`) under the Agentic account, in the same turn. The repo file is the richer record (thesis, added date, status); the Robinhood list is the flat symbol list that should always match its rows.
6. **Auto-merge watchlist-only changes.** For a commit that touches only `memory/watchlist.md` (plus its journal entry) — e.g. from `/watchlist-add` or any other watchlist edit — commit, push, and merge it to `main` in the same turn without waiting for a separate "please merge" instruction. The user has pre-authorized this specifically so the repo file and the Robinhood watchlist never sit out of sync waiting on a merge. This does **not** extend to any other change (skills, routines, commands, code, docs) — those still wait for explicit confirmation before merging, per the repo's normal git workflow.
7. **Auto-merge output from the read-only/report Routines.** Commits produced by running `daily-check`, `weekly-scan`, `earnings-watch`, or `opportunity-scan` — journal entries in `memory/journal/`, and watchlist changes already covered by guardrail 6 — can be committed, pushed, and merged to `main` in the same turn without waiting for approval. The user has pre-authorized this for these four Routines specifically, since none of them place a trade. This does **not** extend to placing or modifying an actual order — guardrail 1 (Propose + Confirm) still requires the user's explicit "yes" before any trade executes, no matter how routine or well-reasoned the setup looks — nor to changes outside a routine's normal output (editing a skill, adding a new routine, changing these guardrails, etc.), which still wait for explicit confirmation before merging.
8. **`opportunity-scan` may self-manage the watchlist; it may also surface trade proposals.** Unlike `weekly-scan` (which still needs the user's confirmation before writing to `memory/watchlist.md`), `opportunity-scan` is pre-authorized to add or remove watchlist symbols directly based on its own findings — same conviction bar used elsewhere in this repo (real signal, no bad news/major concerns for an add; thesis clearly broken or the signal gone for a removal) — and to journal its reasoning rather than ask first. It's also allowed to invoke `propose-trade` when a candidate clears that bar, but doing so is optional — a run with nothing compelling should report that plainly rather than manufacture a proposal. Two things this does **not** change: (a) before proposing an actual trade, it must cross-check the candidate against the most recent `earnings-watch` and `weekly-scan` findings (read their latest relevant journal entries, or run the equivalent live checks — earnings calendar, fundamentals — if nothing recent covers the symbol) so a trade idea isn't proposed on a quick momentum read alone; (b) `propose-trade` still never places an order without the user's explicit confirmation in that conversation, per guardrail 1 — `opportunity-scan` surfacing a proposal is not that confirmation.

## Layout

- `routines/` — playbooks each recurring Routine follows (purpose, schedule, steps, guardrails, journal output)
- `memory/watchlist.md` — current watchlist and thesis per symbol
- `memory/journal/` — one markdown file per day, journaling routine activity and decisions
