# CLAUDE.md

Standing instructions for any Claude Code session — interactive or a scheduled Routine — working in this repo. See `README.md` for the full strategy.

## Guardrails

1. **Autonomous execution, within guardrails.** Once a trade — new position, add, trim, or exit — clears every guardrail below (sizing, position cap, stop-loss, weekly cap) and, for entries, the chase/extension and earnings-timing checks, it can be placed directly without waiting for a separate "yes" from the user in that conversation. This applies to both opening new positions and exiting/trimming existing ones. Every placed order is still journaled in full (guardrail 4) and reported to the user afterward — oversight happens through the record, not a pre-trade approval. `/sell-all` keeps its own explicit confirmation step by design (liquidating every position at once is treated as a distinct, higher-stakes action) — see that command for details.
2. **Agentic account only.** Trade exclusively through the Agentic Robinhood account (••••6245). Do not act on any other linked account.
3. **Respect the risk guardrails** in `README.md` on every proposal: max 20% of account value per position, max 7 concurrent open positions, -8% stop-loss, max 7 new proposals/week. No fixed minimum cash reserve — `propose-trade` sizes each position at its own judgment up to these caps, including up to full deployment when warranted.
4. **Journal every routine run.** After any routine (scheduled or manual) touches the portfolio, watchlist, or a scan, append an entry to `memory/journal/<YYYY-MM-DD>.md` (create the file if today's doesn't exist yet) using the format in `memory/README.md`.
5. **Keep the watchlist current — in both places.** When the user approves adding, removing, or updating the thesis on a symbol, reflect it in `memory/watchlist.md` **and** mirror the add/remove to the Robinhood "Agentic Watchlist" (list_id `aaf2fa51-2240-4463-8af2-d8c8b0621302`, via `add_to_watchlist`/`remove_from_watchlist`) under the Agentic account, in the same turn. The repo file is the richer record (thesis, added date, status); the Robinhood list is the flat symbol list that should always match its rows.
6. **Auto-merge watchlist-only changes.** For a commit that touches only `memory/watchlist.md` (plus its journal entry) — e.g. from `/watchlist-add` or any other watchlist edit — commit, push, and merge it to `main` in the same turn without waiting for a separate "please merge" instruction. The user has pre-authorized this specifically so the repo file and the Robinhood watchlist never sit out of sync waiting on a merge. This does **not** extend to any other change (skills, routines, commands, code, docs) — those still wait for explicit confirmation before merging, per the repo's normal git workflow.
7. **Auto-merge output from the read-only/report Routines — and executed-trade journal entries.** Commits produced by running `daily-check`, `weekly-scan`, `earnings-watch`, or `opportunity-scan` — journal entries in `memory/journal/`, and watchlist changes already covered by guardrail 6 — can be committed, pushed, and merged to `main` in the same turn without waiting for approval. This also covers `propose-trade`'s own journal entry documenting a placed or modified order: since guardrail 1 no longer requires a pre-trade confirmation, there's no separate approval gating the record either — commit, push, and merge it in the same turn once the trade is journaled. This does **not** extend to `/sell-all`'s journal entry, which still waits for the user's explicit "merge it" (that command keeps its own pre-trade confirmation step by design, per guardrail 1). Nor does it extend to changes outside a routine's normal output (editing a skill, adding a new routine, changing these guardrails, etc.), which still wait for explicit confirmation before merging.
8. **`opportunity-scan` may self-manage the watchlist; it may also initiate trades.** Unlike `weekly-scan` (which still needs the user's confirmation before writing to `memory/watchlist.md`), `opportunity-scan` is pre-authorized to add or remove watchlist symbols directly based on its own findings — same conviction bar used elsewhere in this repo (real signal, no bad news/major concerns for an add; thesis clearly broken or the signal gone for a removal) — and to journal its reasoning rather than ask first. It's also allowed to invoke `propose-trade` when a candidate clears that bar, but doing so is optional — a run with nothing compelling should report that plainly rather than manufacture a trade. Two things this does **not** change: (a) before triggering an actual trade, it must cross-check the candidate against the most recent `earnings-watch` and `weekly-scan` findings (read their latest relevant journal entries, or run the equivalent live checks — earnings calendar, fundamentals — if nothing recent covers the symbol) so a trade idea isn't acted on from a quick momentum read alone; (b) `propose-trade` places the order directly once its own checks pass, per guardrail 1 — there's no separate confirmation step, so `opportunity-scan` invoking it on a candidate that clears the bar results in an executed trade, not just a proposal.

## Layout

- `routines/` — playbooks each recurring Routine follows (purpose, schedule, steps, guardrails, journal output)
- `memory/watchlist.md` — current watchlist and thesis per symbol
- `memory/journal/` — one markdown file per day, journaling routine activity and decisions
